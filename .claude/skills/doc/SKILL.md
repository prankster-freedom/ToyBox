# doc（ドキュメントのメンテナンス）

ドキュメントの整合を確認し、メンテナンスする。

対象: $ARGUMENTS

## 呼び出し方による違い

| 呼び出し方                                    | 対象範囲                                             | 【承認】 |
| :-------------------------------------------- | :--------------------------------------------------- | :------- |
| ユーザーが `/doc` で明示的に呼び出す          | 指定したフォルダ・ファイル（省略時はリポジトリ全体） | 下記の手順どおり承認を得る |
| Markdown の作成・修正中に AI が自動で読み込む | 文脈に応じた範囲（作成・修正中のファイルと、それを参照する・参照されるファイル）。リポジトリ全体は対象にしない | 本スキルとしての承認は不要。手順 3・5 を省き、確認結果と修正内容は元の作業の報告に含める |

自動で読み込んだ場合も、元の作業（swe1 などのスキルや依頼された作業）に【承認】の工程があれば、それに従う。判断できない矛盾は、推測で決めずに質問する。

## 手順

1. **対象範囲の確認**: 対象が指定されている場合は、そのフォルダ・ファイルと、それを参照する・参照されるファイルを対象とする。指定されていない場合は、リポジトリ全体を対象とする。
2. **調査**: 次の観点で問題を洗い出す。
   - ドキュメント間の矛盾・不整合（同じ事柄について記述が食い違っていないか）
   - リンク切れ・存在しないファイルへの参照
   - README などの一覧・目次と、実在するファイルとのずれ
   - 下記「格納先」に合わない配置、Front Matter の欠落
   - 単位ごとの `README.md`・版番号・リリースノートの欠落や不一致（`AGENTS.md` 1.9）
   - ソフトウェアの単位の `README.md` に、使い方（最も簡単な使い方と、主な使い方のパターン）があるか
   - 下記「作業ファイル」に当たるもの（テスト結果、生成物など）がリポジトリに入っていないか
   - 工程間のトレーサビリティ（`AGENTS.md` 1.4）の ID 参照の切れ

   矛盾がある場合は、コミット履歴・チャットログ・GitHub Issues を参考に、どちらの記述を正とするかを判断する。
3. **【承認】修正方針の提示**: 見つかった問題ごとに、対象ファイル・修正内容・正とする記述とその根拠を示し、承認を得る。判断できない矛盾は、推測で決めずに質問する。
4. **修正**: 承認された方針に沿って修正する。仕様書・設計書・テスト結果以外の付帯成果物（README、運用資料など）も、必要なものは作成・更新する。
5. **【承認】結果の確認**: 修正したファイルと変更の要点、未解決の事項を報告し、承認を得たら完了とする。

## 格納先

ドキュメントの種類に応じて、次の場所に置く。既存のプロジェクトで別の構成が定着している場合はそれに従い、移動するかどうかはユーザーに確認する。

| 種類                                   | 格納先                        | 例                                         |
| :------------------------------------- | :---------------------------- | :----------------------------------------- |
| リポジトリ全体に関係するドキュメント   | リポジトリ直下                | `README.md`, `AGENTS.md`, `CLAUDE.md`      |
| リポジトリ固有の資料                   | `AGENTS.repo.md` に定める     | テーマ別のナレッジ、ブランチ戦略など       |
| ソフトウェアプロジェクトのドキュメント | `<プロジェクト>/doc/`（下表） | 要求仕様書、設計書、テスト仕様書、変更要求 |
| AI エージェントの設定                  | 原則は `AGENTS.md`、スキルは `.claude/skills/`。ツール固有の設定のみ `.claude/`, `.cursor/` | 原則、スキル、ツール固有の設定（`AGENTS.md` 3 章） |

### ソフトウェアプロジェクトのドキュメント

swe1〜test の各スキルは、次の格納先を使う。番号は工程の順に対応させる。

| 工程   | 種類                         | 格納先                                                         |
| :----- | :--------------------------- | :------------------------------------------------------------- |
| swe1   | 要求仕様書                   | `<プロジェクト>/doc/1.SPEC.md`                                 |
| swe2-1 | アーキテクチャ設計書         | `<プロジェクト>/doc/2.ARCHITECTURE.md`                         |
| swe3-1 | 詳細設計書（機能単位）       | `<プロジェクト>/doc/3.detailed_design/features/<feature名>.md` |
| swe3-2 | 実装ドキュメント（ソースと 1:1） | `<プロジェクト>/doc/4.implementation/<ソースのパス>.md`    |
| test   | テスト仕様書（feature 単位） | `<プロジェクト>/doc/5.test_spec/<サービス>/<feature名>.md`（目次は `doc/5.test_spec/README.md`） |
| cr     | 変更要求（CR）               | `<プロジェクト>/doc/6.change_request/<サービス>/CR-<SVC>-<nnn>_<件名>.md`（一覧は `doc/6.change_request/README.md`） |
| doc    | 運用資料                     | `<プロジェクト>/doc/9.運用資料_<名称>.md`（例: 初期設定マニュアル、エンドユーザー向けマニュアル） |

サービスが 1 つのプロジェクトでは、`<サービス>` の階層を省略できる。

### 作業ファイル（git 管理外）

変換の出力、中間ファイル、テストの出力、テスト結果、補助スクリプトなどの作業ファイルは、`<プロジェクト>/work/`（git 管理外）に置く。リポジトリには残さない。

| 種類           | 格納先                                                      |
| :------------- | :---------------------------------------------------------- |
| テスト結果     | `<プロジェクト>/work/test_result/yyyy-mm-dd-<feature名>.md` |
| テストの出力   | `<プロジェクト>/work/test/`                                 |
| 補助スクリプト | `<プロジェクト>/work/tools/`                                |

## 表の書き方

Markdown の表は、プレーンテキストを等幅フォントで表示したときにも読みやすいように、各行の列の位置（`|` の位置）を揃える。

- 全角文字は半角 2 文字分の幅として数える
- 各列の幅は、その列で最も長いセルに合わせ、短いセルは末尾を空白で埋める
- 区切り行（`| :--- |`）も列の幅に合わせて `-` を伸ばす
- 表の 1 行の幅は半角 120 文字程度までを目安とする。目安を超える場合は、長いセルを例外として列幅の計算から外し、他のセル同士で列幅を揃える
  - 途中の列: 特定の行（目安としてデータ行の 3 分の 1 まで）だけに長いセルがある場合、そのセルを例外にする。例外の行は、長いセルより前の列だけ位置を揃え、長いセルとそれより後ろは空白を 1 つ空けて続ける
  - 最後の列: 長いセルが多くの行にあっても、例外にしてよい。目安に収まる行同士で列幅を揃え、長いセルは空白で埋めずにそのまま書く
- 途中の列で多くの行が目安を超える場合は、セルの内容を短くするか、表を箇条書きに変える
- 整形には `agents-support-tools/md-table-align/` のスクリプトを使える（使い方は同フォルダの `README.md`）

## ID 体系

工程間・文書間のトレーサビリティ（`AGENTS.md` 1.4）のため、次の形式で ID を付ける。サービス → feature → 連番の階層とし、`<SVC>`（サービス）と `<FEAT>`（feature）は英大文字の略号とする。略号の一覧は、要求仕様書・テスト仕様の目次・CR の一覧で定義する。

| 種別                 | 形式                                 | 例            | 定義する文書 |
| :------------------- | :----------------------------------- | :------------ | :----------- |
| 機能要求・非機能要求 | `FR-<SVC>-<nnn>` / `NFR-<SVC>-<nnn>` | `FR-SHOP-001` | 要求仕様書   |
| 詳細設計             | `DD-<FEAT>-<nnn>`                    | `DD-AUTH-001` | 詳細設計書   |
| テストケース         | `TC-<FEAT>-<nnn>`                    | `TC-AUTH-001` | テスト仕様書 |
| 変更要求             | `CR-<SVC>-<nnn>`                     | `CR-SHOP-001` | 変更要求     |

サービスが 1 つのプロジェクトでは `<SVC>` を省略できる（例: `FR-001`）。

テスト仕様と CR には、対応・影響する FR / DD / TC / CR の ID を記載する。テスト結果には TC の ID ごとに結果を記載する。
