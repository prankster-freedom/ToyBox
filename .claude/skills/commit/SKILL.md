# commit

ユーザーからコミットの指示があった場合にのみ、この手順を実行する。コミットの指示がコミット実施の承認を兼ねるため、本スキルに【承認】の工程はない。ユーザーの承認を待たずにコミットまで進める。ただし **push はユーザーから push の指示を受けたときのみ** 行う。

補足指示: $ARGUMENTS

## 現在の状態

- ブランチ: !`git branch --show-current`
- 変更ファイル:

!`git status --short`

## 手順

1. **ブランチ, Pull Request, GitHub Issue の確認**
   既に feature ブランチをチェックアウトしているかどうかや Pull Request が作成済みかどうか、関連する GitHub Issue が存在するかを確認する（例: `git branch -a`、`gh pr list`、`gh issue list`）。
   確認結果に応じて対応する。
   - feature ブランチ上の場合: 現在の差分がそのブランチの目的に沿うかを判断し、沿うならそのままコミットへ進む。
   - main などのデフォルトブランチ上の場合、または差分がブランチの目的と明らかに異なる場合: コミット前にブランチの作成・切り替えをユーザーに問い合わせる。
   - PR の作成は push を伴うため、ユーザーから指示があるときのみ行う。
   - ブランチを新しく作るときは、下記「ブランチ規則」に従って命名する。
2. `git status`, `git diff` で変更内容を確認する。コミットすべきでないもの（秘密情報、一時ファイル、壊れた参照など）を見つけた場合は、コミットせずにユーザーへ報告する。
3. 変更をコミット単位に分割し、下記「コミットメッセージ規約」に従って `git commit` を実行する。
4. 作成したコミットをレビューする（`git log`, `git show --stat` など）。
   - 観点: 分割単位（1 コミット 1 単位）、メッセージの規約準拠、型と版の上げ方の対応、対象ファイルの過不足、参照切れ
   - 問題があれば、未 push のコミットに限り `git commit --amend` や `reset` などで修正する。push 済みのコミットは書き換えず、ユーザーに相談する。
5. 結果（コミット ID・メッセージ・対象ファイル・レビューで直した点）をユーザーに報告する。push は行わず、ユーザーから push の指示を受けたときのみ `git push` する。

## ブランチ規則

- **main へのマージは必ず Pull Request を経由する。** main へ直接 commit・push・マージしてはならない。
- **main へのマージは Rebase and merge（fast-forward で履歴を一直線にする）のみとする。** マージコミットの作成と Squash merge は禁止する（リポジトリの設定でも Rebase and merge だけを許可している）。
- Rebase and merge ではコミットのハッシュが変わる。タグは、マージ後の main 上のコミットに付ける。
- feature ブランチは `feature/<変更内容>` とする（ケバブケース。例: `feature/cw-restore`）。
- ソフトウェア開発でフィーチャー単位に分ける場合は `feature/<feature名>/<CR番号または変更内容>` とする。

## コミットメッセージ規約

- **Conventional Commits 1.0.0 に従うこと（必須）**
- 形式: `[<チケット番号>] <型>[任意のスコープ]: <タイトル>`。必要なら空行のあと本文・フッター
- `[<チケット番号>]` は関連するチケットの番号（例: `[ADADAS-xxxxx]`）。チケットがない場合は付けない
- Markdown ファイルの変更は、Conventional Commits の例外として、型を常に `doc` にする（例: `doc(commit)!: …`、`doc(cr): … を追加する`）。変更の種類は `doc:` の後の説明で区別する。`doc` は版を上げない（`AGENTS.md` 1.9）。Markdown 以外のファイルの変更は、下表の型を使う。release スキルのリリースコミット（`chore(release): …`）は、この例外の対象外とする
- リポジトリ固有の例外（チケット番号の付け方、型の例外など）は `AGENTS.repo.md` に従い、本スキルの規約より優先する
- 型は、その変更をリリースしたときの版の上げ方（`AGENTS.md` 1.9）に合わせて選ぶ

  | 型                                                  | 使う変更                                                                               | 版    |
  | :-------------------------------------------------- | :------------------------------------------------------------------------------------- | :---- |
  | `feat`                                              | 機能・手順・節・内容の追加                                                             | MINOR |
  | `fix`                                               | 誤り・誤字・リンク切れの修正                                                           | PATCH |
  | `feat!` / `fix!`、またはフッター `BREAKING CHANGE:` | 従来の使い方・手順と互換がなくなる変更（手順や禁止事項の変更、ファイルや節の削除など） | MAJOR |
  | `docs` / `style` / `refactor` / `chore` / `test` / `ci` / `build` / `perf` | 単位の内容に影響しない変更（単位に属さない README の一覧の更新、書式の整理など） | 上げない |

- スコープは変更した単位の名前（例: `swe1`, `sample-app`）。単位に属さない変更は、変更箇所を表す短い名詞（例: `claude`, `gitignore`）
- 1 つのコミットでは、原則として 1 つの単位だけを変更する
- **共有ファイルの変更は、独立したコミットにする。** 共有ファイル（`AGENTS.md` 4 章）は複数のリポジトリで同じ内容にするため、その変更は、共有ファイル以外の変更（`AGENTS.repo.md` を含む）と同じコミットに混ぜない。他のリポジトリへ cherry-pick してそのまま PR を出せるようにするため
- 型が異なる変更（例: `feat` と `fix`）は、可能な限りコミットを分割する
- 版番号はコミットでは変更しない（リリースのときに release スキルで上げる）
- タイトル・本文は日本語。タイトルはそのままリリースノートに載るため、何が変わったかが読み手に伝わる短い要約とし、詳細・経緯・根拠は本文へ回す
- タイトル末尾に句点「。」を付けない。タイトルに実装詳細の羅列や全角括弧での補足を詰め込まない
- コミットメッセージと Pull Request の説明文に、AI ツールによる生成の表示（`Generated with …` などの署名、`Co-Authored-By:` による AI の共同作成者の表示）を入れない。AI ツールの既定の設定で付く場合も入れない

良い例:

| 対象     | 例                                                                        |
| :------- | :------------------------------------------------------------------------ |
| コード   | `feat(sample-app): CSV 形式でのエクスポートに対応する`                    |
| コード   | `fix(sample-app): 空の入力で保存すると異常終了する不具合を修正する`       |
| コード   | `feat(sample-app)!: 設定ファイルの形式を YAML に変更する`                 |
| Markdown | `doc(swe1): 要求仕様書のひな形を追加する`                                 |
| Markdown | `doc(control-system-documentation): 存在しないファイルへの参照を削除する` |

悪い例:

| 対象     | 例                                         | 問題点                                                       |
| :------- | :----------------------------------------- | :----------------------------------------------------------- |
| コード   | `更新しました`                             | 型・要約がない                                               |
| コード   | `fix(sample-app): バグ修正。`              | 何が変わったか伝わらない。末尾に句点がある                   |
| コード   | `docs(sample-app): ログイン画面にパスワード表示ボタンを追加する` | 機能の追加なのに型が `docs`（`feat` にする） |
| コード   | `feat(sample-app): v1.1.0 にする`          | 版番号をコミットで変更している（版はリリースのときに上げる） |
| Markdown | `feat(swe1): 要求仕様書のひな形を追加する` | Markdown の変更なのに型が `feat`（`doc` にする）             |
| Markdown | `doc: AGENTS.md と sample-app の README を更新する` | 共有ファイルとそれ以外の変更を 1 つのコミットに混ぜている |
