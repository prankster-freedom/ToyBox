# swe3（SWE.3: ソフトウェア詳細設計と実装）

詳細設計と実装を行う。ソフトウェア開発の工程は swe1 → swe2 → swe3 → test → commit の順に進める。

対象: $ARGUMENTS

## Work Product (WP: 成果物)

1. **ソースコード**: プロダクトのソースコード
2. **Design Notes**（ソースコード本文やソースコード内コメントだけでは不十分な場合）: `<プロジェクト>/doc/DesignNotes/<対象>.md`
   - コードから読み取りにくい間接的な依存、変更すると壊しやすい点、設計判断の背景・根拠など、コードやインラインコメントだけでは表現しきれない重要な設計情報を記録する。
   - コードを読めば分かること（関数一覧、処理の流れなど）は二重管理となるため書かない。

## 手順

1. **前提の確認**: 対象機能の要求仕様（SRS）およびアーキテクチャ設計（ADS）が承認済みであることを確認する。未承認または不足がある場合は、前工程（swe1 または swe2）に戻ることを提案する。
2. **【承認】実装・詳細設計計画の確認**: 変更・追加するファイル、実装方針、実装の順序と単位、追加する依存ライブラリ、実行するコマンド、作業規模の見積もり（`AGENTS.md` 1.11）を示し、承認を得る。
3. **実装**: 承認された計画の単位ごとに実装し、その都度結果を報告する。
   - 計画にない変更（ファイルの追加、依存ライブラリの追加、計画外のコマンド実行など）が必要になった場合は、着手前に承認を得る
   - ソースコード本文やコメントだけで十分な場合は余計なドキュメントを作成せず、コード内に簡潔かつ十分なコメントを残す
   - コードから読み取りにくい重要な構造・依存関係や設計判断の背景がある場合のみ、Design Notes を作成・更新する
4. **【承認】結果の確認**: 変更したファイル、実装内容と要求との対応、未解決の事項を報告し、承認を得たら完了とする。

## 実装のルール

- 新規機能は、まずスケルトン（関数、API、イベントハンドラなど）から実装し、次に詳細ロジックを実装する。呼び出し前後のエラー判定や例外処理も実装する。
- 処理の把握しやすさや保守性を保つため、1 つの関数は最大でも 80 行程度に収める。
- サーバーの起動や外部 API の呼び出しなどの動的な動作確認は行わない。ローカルの CLI をサンプルデータで実行する開発中の確認は、実装計画に明記して承認を得れば行ってよい（出力は `<プロジェクト>/work/`）。正式な検証は test スキルで行う。
- CLI の引数や使い方を変えたら、単位の `README.md` の使い方も更新する。
