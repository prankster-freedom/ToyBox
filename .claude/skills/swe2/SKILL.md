# swe2（SWE.2: ソフトウェアアーキテクチャ設計とブランチ作成）

アーキテクチャ設計とブランチ作成、計画の更新を行う。ソフトウェア開発の工程は swe1 → swe2 → swe3 → test → commit の順に進める。

対象: $ARGUMENTS

## Work Product (WP: 成果物)

1. **ADS (Architecture Design Specification)**: `<プロジェクト>/doc/ADS.md`（または `doc/2.ARCHITECTURE.md`）
   - システム全体のアーキテクチャ、構成要素（コンポーネント分割・配置）、利用技術の選定
   - コンポーネント間のインターフェースおよびデータフロー
   - 設計判断の背景・根拠、採らなかった案とその理由
   - 各要素と要求仕様 ID（FR / NFR）のトレーサビリティ
2. **SwcRS (Software Component Requirement Specification)**: `<プロジェクト>/doc/SwcRS/<コンポーネント名>.md`
   - 詳細な要求仕様を定義したほうが良い SWC（ソフトウェアコンポーネント）についてのみ作成する

## 手順

1. **既存の設計書の確認**: ワークスペースにアーキテクチャ設計書が既に存在するかを確認する（格納先は doc スキルの「ソフトウェアプロジェクトのドキュメント」）。
   - 存在する場合: 既存の内容を十分に理解し、それをベースに作業を進める
   - 存在しない場合: 新規に作成する
2. **アーキテクチャ設計案の作成**: arc42 などの確立されたテンプレートを参考に、アーキテクチャ設計（ADS）を構造化して記述する。また、複雑なコンポーネント等で必要と判断される場合は SwcRS を作成する。設計の各要素には、対応する要求仕様の ID（`FR-xxx` / `NFR-xxx`）を記載する。
3. **【承認】設計案とブランチ戦略の確認**: アーキテクチャと利用技術の案、ブランチ戦略（ブランチ名は commit スキルの「ブランチ規則」に従う）をユーザーと協議し、承認を得る。前工程の計画に変更が出た場合は、あわせて提示する。
4. **反映とブランチ作成**: 承認された内容を設計書に反映し、承認されたブランチを作成する。
   - 設計判断の背景・根拠（なぜその構成・技術にしたか、前提とした制約、採らなかった案とその理由など）は、後の設計変更でのデグレを防ぐため、該当する設計要素の近くに記載する
   - 議論の経緯（いつ・誰が・どのようなやり取りで決めたか）は設計書に書かず、コミットメッセージの本文に残す（`AGENTS.md` 1.9）
5. **【承認】最終版の確認**: 最終版のドキュメントをユーザーに報告し、明示的に承認を得たら完了とする。
