# swe3-2（implementation / 工程 3-2: 実装）

実装を行う。

対象: $ARGUMENTS

## 手順

1. **前提の確認**: 対象の詳細設計書が承認済みであることを確認する。未承認または不足がある場合は、swe3-1 に戻ることを提案する。
2. **【承認】実装計画の確認**: 変更・追加するファイル、実装の順序と単位、追加する依存ライブラリ、実行するコマンド、作業の規模の見積もり（`AGENTS.md` 1.11）を示し、承認を得る。
3. **実装**: 承認された計画の単位ごとに実装し、その都度結果を報告する。
   - 計画にない変更（ファイルの追加、依存ライブラリの追加、計画外のコマンド実行など）が必要になった場合は、着手前に承認を得る
   - あわせて、下記「実装ドキュメント」を作成・更新する
4. **【承認】結果の確認**: 変更したファイル、詳細設計との対応、未解決の事項を報告し、承認を得たら完了とする。

## 実装のルール

- 新規機能は、まずスケルトン（関数、API、イベントハンドラなど）から実装し、次に詳細ロジックを実装する。呼び出し前後のエラー判定や例外処理も実装する。
- 処理の把握しやすさや保守性を保つため、1 つの関数は最大でも 80 行程度に収める。
- サーバーの起動や外部 API の呼び出しなどの動的な動作確認は行わない。ローカルの CLI をサンプルデータで実行する開発中の確認は、実装計画に明記して承認を得れば行ってよい（出力は `<プロジェクト>/work/`）。正式な検証は test スキルで行う。
- CLI の引数や使い方を変えたら、単位の `README.md` の使い方も更新する。

## 実装ドキュメント

- **ディレクトリ構成**: **ソースコードと 1:1 の構造** を保ち、`<プロジェクト>/doc/4.implementation/` 以下に作成する（例: `lib/auth.js` → `doc/4.implementation/lib/auth.js.md`）。ひな形は [template.md](template.md)。
- **依存関係図（Mermaid）**: 各ドキュメントには、Mermaid（`flowchart TD`）で依存関係を必ず記述する。
  - **Dependencies**: そのモジュールが使用しているライブラリやモジュール
  - **Consumers**: そのモジュールを使用している（依存している）モジュール
  - **構文**: ノード名に特殊文字が含まれる場合は、必ずダブルクォートで囲む（例: `id["@scope/pkg"]`）。記法の詳細は markdown-plantuml-documentation スキルを参照する
- 各ドキュメントには、対応する詳細設計の ID を記載する。
