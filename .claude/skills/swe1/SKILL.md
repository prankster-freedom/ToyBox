# swe1（工程 1: 要求獲得と要求分析、計画）

要求獲得と要求分析、計画を行う。ソフトウェア開発の工程は swe1 → swe2-1 → swe3-1 → swe3-2 → test → commit の順に進める。

対象: $ARGUMENTS

## 手順

1. **既存の仕様書の確認**: ワークスペースに要求仕様書が既に存在するかを確認する（格納先は doc スキルの「ソフトウェアプロジェクトのドキュメント」）。
   - 存在する場合: 既存の内容を十分に理解し、それをベースに作業を進める
   - 存在しない場合: [template.md](template.md) のひな形を使って新規に作成する
   - 既存の仕様書が要求・設計を兼ねている場合は、ユーザーの承認を得てそれを代用し、要求・設計の ID と仕様書の節の対応を記録する
2. **要求の分析**:
   - 既存の要求事項を確認し、不明点があれば質問する
   - 新たな要求の追加や変更が必要な場合は提案する
   - ドキュメントの構成や文章表現に改善の余地がある場合は、具体的な修正案を提案する
   - 機能要求（FR）、非機能要求（NFR）を ID で管理する（例: `FR-001`, `NFR-001`）
3. **【承認】変更案と作業計画の確認**: 要求仕様の変更案と、次の工程以降の作業計画をユーザーと協議し、承認を得る。
4. **要求仕様書への反映**: 承認された内容を要求仕様書に反映する。
   - 要求の背景・根拠（なぜその要求が必要か、前提とした制約、採らなかった案とその理由など）は、後の仕様変更でのデグレを防ぐため、該当する要求の近くに記載する
   - 議論の経緯（いつ・誰が・どのようなやり取りで決めたか）は要求仕様書に書かず、コミットメッセージの本文に残す（`AGENTS.md` 1.9）
   - ユースケース図やシーケンス図は、PlantUML 形式で要求仕様書の中に直接記載する
   - **シーケンス図には、システムとアクターの間のやり取りだけを記載する。** システム内部の機能間のやり取りは設計情報のため、記載しない
5. **【承認】最終版の確認**: 最終版のドキュメントをユーザーに報告し、明示的に承認を得たら完了とする。
