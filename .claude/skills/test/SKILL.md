# test（工程 4: テスト）

テストを実施する。テスト仕様書はリポジトリ（`doc/`）で管理し、テスト結果とテストの出力は作業ディレクトリ（`work/`、git 管理外）に置く。格納先と ID 体系は doc スキルの「ソフトウェアプロジェクトのドキュメント」「作業ファイル」「ID 体系」に従う。

対象: $ARGUMENTS

## 手順

1. **【承認】テスト仕様の作成・更新**: `<プロジェクト>/doc/5.test_spec/<サービス>/<feature名>.md` に、テストケース（`TC-<FEAT>-<nnn>`）・観点・手順・期待結果・対応する要求・設計・変更要求の ID（FR / DD / CR）と、実行するコマンド、作業の規模の見積もりを記載し、承認を得る。ひな形は [spec_template.md](spec_template.md)。
   - 期待結果は、要求に基づく条件で書く。実装の結果をそのまま固定値（件数など）にしない
   - 既存のテストケースを変更・廃止する場合は、ID を再利用しない。廃止・置き換えた TC の ID と代わりの TC の ID の対応、変更・廃止の背景・根拠（なぜ変えたか、対応する要求・設計・変更要求の ID など）は、後の変更でのデグレを防ぐため、テスト仕様書の表に残す
   - 議論の経緯（いつ・誰が・どのようなやり取りで決めたか）はテスト仕様書に書かず、コミットメッセージの本文に残す（`AGENTS.md` 1.9）
2. **テストの実施**: 承認されたテスト仕様に沿ってテストを実施する。
   - テストの出力は `<プロジェクト>/work/test/` に置く。再実行の前に、前回の出力を別のフォルダに残す
   - テスト仕様にないコマンドの実行が必要になった場合は、着手前に承認を得る
   - 画面の見た目に関わる自動確認では、要素があることだけでなく、利用者に見分けられること（背景と異なる色、他の要素と重ならないこと、判読できる大きさ）まで確かめる。要素の有無だけの確認では、背景と同じ色の文字のような不具合を見逃す
   - 表示倍率や寸法の自動確認では、下限や上限の不等式だけでなく、期待値との一致（等値性・許容誤差）まで厳密に確かめる。不等式のみの緩い判定（例: 原寸以上であることのみの確認）では、意図しない肥大化や縮小・倍率逆転などの不具合を見逃す
   - 目視確認で見つけた不具合のうち、自動で確かめられるものは、修正とあわせてテスト仕様に TC を追加する（または既存の TC の期待結果に加える）
3. **結果の記録**: テスト結果を `<プロジェクト>/work/test_result/yyyy-mm-dd-<feature名>.md`（git 管理外）に保存する（例: `2025-12-12-auth-login.md`）。ひな形は [template.md](template.md)。
   - テスト仕様の TC ID ごとに結果を記載する
   - 修正後の再テストは、同じファイルに「再テスト」の節を追加する
4. **【承認】結果のレビュー**: テスト結果をユーザーとレビューし、明示的に承認を得たら完了とする。不合格のテストがある場合は、前工程（swe3 や swe2）に戻るか、変更要求（cr スキル）として登録するかを提案する。
   - 不合格ではない所見（改善の余地）は、git 管理外のテスト結果だけに残すと、他の作業者や AI から見えない。ユーザーと合意したうえで、変更要求（cr スキル）として登録するか、単位の `README.md` の「既知の課題」に記載する
