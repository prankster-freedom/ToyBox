# dtp（DTP・エディトリアルデザイン設計と校正）

出版物の制作工程（企画・基本設計 → ラフ・台割り → レイアウト設計 → 素材準備 → 組版 → 校正・校了）に基づき、プロダクトやドキュメントの視覚デザイン設計と、実装・テスト完了後のデザイン校正（初校・赤字・再校・校了）を行う。

対象: $ARGUMENTS

## エンジニアリング工程との関係性

デザインを伴う開発では、次の順序で工程を進める。

`dtp（設計）` → `swe1` → `swe2` → `swe3` → `test` → `dtp（校正）` → `commit`

1. **前段（Phase 1: デザイン設計）**: 本スキルで基本フォーマット、ラフ（ボツ案・保留ストック含む）、レイアウト、素材を設計・選定する。成果物（WP）である確定デザイン仕様書（`doc/DTP/`）と本番素材（`assets/`）が、エンジニアリング工程（`swe1` → `swe2` → `swe3`）のインプットとなる。
2. **エンジニアリング工程（組版・実装・機能検証）**: `swe1`（要求定義）〜`swe3`（実装）でデザイン仕様を反映して組版・実装を行い、`test` で機能・表示テストを完了させる。
3. **後段（Phase 2: 校正・デザインチェック）**: `test` 完了後、実際の描画出力（ゲラ）をデザイン仕様書と突き合わせて校正を行う。赤字（修正指示）があれば前工程（`swe3` 等）へ差し戻して再校を行い、すべての赤字が解消されて「校了」となったら `commit` へ進む。

## Work Product (WP: 成果物) とフォルダ階層

製品に同梱（SaaS の場合は公開配信）する本番素材と、リリースから除外するデザイン仕様・ラフ・ストック素材をディレクトリ単位で分離する。リリース・デプロイ時は `doc/` と `work/` を除外するだけで、未使用のストックやボツネタが本番環境に混入しない構成とする。

```text
<プロジェクト>/
├── assets/                        # 【リリース同梱・公開対象】製品で実際に使用する確定素材のみを配置
│   ├── images/                    #   本番用の画像・イラスト・写真
│   ├── icons/                     #   本番用のアイコン・シンボル（SVG 等）
│   └── fonts/                     #   同梱が必要な場合の Web フォント等
│
├── doc/
│   └── DTP/                       # 【リリース除外対象】デザイン仕様・ラフ・ストック管理（doc/ ごと除外可能）
│       ├── README.md              #   DTP 全体設計書・目次（トーン＆マナー、判型/グリッド、配色、タイポグラフィ、DTP ID 一覧）
│       ├── features/              #   エンジニアリング（swe1〜swe3）へ渡す確定デザイン仕様書
│       │   └── <feature名>.md     #     feature 別のレイアウト仕様、組版ルール、使用する本番素材 ID（AST-xxx）
│       ├── roughs/                #   ラフ案・レイアウト検討ストック（採用案の原型・ボツネタ・保留ストック）
│       │   ├── README.md          #     ラフ案台帳（ID `RGH-<nnn>`、状態［採用 / ストック / ボツ］、採否理由・再利用条件）
│       │   ├── adopted/           #     採用されたラフスケッチ・ワイヤーフレーム（記録用）
│       │   └── stock/             #     ボツネタ・保留ラフ案（今後の別機能や別スタイルで再利用しうるストック）
│       └── assets/                #   素材管理台帳と非公開ストック置き場
│           ├── README.md          #     素材台帳（ID `AST-<nnn>`、状態［使用中 / ストック / ボツ］、配置パス、仕様・権利情報）
│           ├── sources/           #     加工前の元データ・制作ファイル（リリースには含めない元 SVG/デザインデータ等）
│           └── stock/             #     未使用のストック素材・ボツ素材の実体ファイル
│
└── work/
    └── dtp_review/                # 【git 管理外・リリース除外】test 完了後のデザイン校正（ゲラ・赤字指示書）
        ├── yyyy-mm-dd-<feature名>.md # 校正結果・赤字指示書・校了記録
        └── galley/                #   校正時に取得したスクリーンショットや出力 HTML/画像（ゲラ）
```

### ID 体系とトレーサビリティ

| 種別         | 形式               | 例              | 定義する文書                                           |
| :----------- | :----------------- | :-------------- | :----------------------------------------------------- |
| デザイン仕様 | `DTP-<FEAT>-<nnn>` | `DTP-THEME-001` | `doc/DTP/README.md`, `doc/DTP/features/<feature名>.md` |
| ラフ案       | `RGH-<nnn>`        | `RGH-001`       | `doc/DTP/roughs/README.md`                             |
| 素材         | `AST-<nnn>`        | `AST-001`       | `doc/DTP/assets/README.md`                             |

- 単一機能または全体共通のデザイン仕様では `<FEAT>` を省略できる（例: `DTP-001`）。
- `swe1`〜`test` のドキュメントでは、対応する `DTP-<FEAT>-<nnn>` や `AST-<nnn>` を参照してトレーサビリティを保つ。

### 素材のライフサイクル（ストックから本番同梱への昇格ルール）

1. **検討・収集時**: 候補となる素材はすべて `<プロジェクト>/doc/DTP/assets/stock/`（加工前元データは `sources/`）に格納し、`doc/DTP/assets/README.md` に `AST-<nnn>` として登録する。
2. **採用決定時（昇格）**: 製品への採用が決まった素材（状態: `使用中`）のみ、本番用に最適化したファイルを **`<プロジェクト>/assets/`** へ配置する。製品コード（HTML/CSS/JS 等）からは `<プロジェクト>/assets/` 内のパスのみを参照し、`doc/DTP/` 配下は直接参照しない。
3. **不採用・廃止時（降格・ストック化）**: ラフ段階で不採用となった素材や、仕様変更で使われなくなった素材は `<プロジェクト>/assets/` から外し、`doc/DTP/assets/stock/` に保管したうえで、台帳の状態を `ストック` または `ボツ`（不採用理由・再利用条件付き）に更新する。

## 手順（Phase 1: デザイン設計 — エンジニアリングの前段）

1. **既存のデザイン資産の確認**: `<プロジェクト>/doc/DTP/` および `<プロジェクト>/assets/` を確認する。
   - 過去のラフ案（`roughs/stock/`）や素材ストック（`assets/stock/`）に再利用できるものがあるかを確認する。
2. **企画・ラフ・レイアウト・素材の検討**:
   - **企画・基本フォーマット**: ターゲット・目的に合わせたトーン＆マナー（世界観、配色パレット、フォント体系、見出しと本文のジャンプ率）と、版面・グリッドシステム（マージン、カラム割、整列基準）を設計する。
   - **ラフ（台割り・構成案）**: 要素の配置バランス、主従関係（視覚的ウェイト）、視線誘導（Z 型・F 型など）のラフ案を複数検討し、`RGH-<nnn>` を付与する。採らなかった案（ボツネタ・保留案）も削除せず、不採用理由や別の場面での活用可能性を整理する。
   - **素材の準備・整理**: 必要な図版、アイコン、装飾パーツ、テクスチャ等を洗い出し、解像度・ベクター仕様・カラー・余白・権利情報を確認して `AST-<nnn>` を付与する。
3. **【承認】デザイン方針・ラフ・採用素材の確認**: 基本フォーマット、ラフ案の採否（採用案とストック／ボツ案）、本番採用する素材（`AST-<nnn>`）、および確定デザイン仕様（`DTP-<FEAT>-<nnn>`）の案をユーザーに提示し、承認を得る。
4. **WP の反映と本番素材の配置**:
   - 全体設計を `doc/DTP/README.md`、feature 別仕様を `doc/DTP/features/<feature名>.md` に反映する。
   - 採用ラフを `doc/DTP/roughs/adopted/`、ボツ・保留ラフを `doc/DTP/roughs/stock/` に保存し、`doc/DTP/roughs/README.md` の台帳を更新する。
   - 採用素材を `<プロジェクト>/assets/` に配置し、未採用・元データを `doc/DTP/assets/stock/`・`sources/` に保存して、`doc/DTP/assets/README.md` の台帳を更新する。
5. **【承認】設計 WP の最終確認**: 作成・更新した WP 一式を報告し、承認を得たら Phase 1 完了とする。続けてエンジニアリング工程（`swe1`〜`test`）へインプットとして引き継ぐ。

## 手順（Phase 2: 校正・デザインチェック — `test` 完了後）

1. **ゲラ（描画出力）の用意**: `test` 工程が完了していることを確認し、対象機能の実際の表示結果（スクリーンショット、出力 HTML/SVG/画像等）を `<プロジェクト>/work/dtp_review/galley/` に取得する。再実行時は前回のゲラを別フォルダへ退避する（`AGENTS.md` 1.10）。
2. **校正（デザインチェック）の実施**: 取得したゲラを、`doc/DTP/` の確定デザイン仕様（`DTP-<FEAT>-<nnn>`）および下記の「校正チェックリスト」と突き合わせて検査する。
3. **校正結果（赤字指示書）の記録**: 検査結果を `<プロジェクト>/work/dtp_review/yyyy-mm-dd-<feature名>.md`（git 管理外）に記録する。
   - 各 `DTP-<FEAT>-<nnn>` およびチェック観点ごとに判定（`校了（OK）` / `赤字（要修正）` / `所見（将来改善）`）を記載する。
   - `赤字（要修正）` がある場合は、具体的な崩れの内容・原因箇所・修正指示（赤字）を明記する。
   - 修正後の再校正（再校・三校）は、同じファイルに「再校」の節を追記して追跡する。
4. **【承認】校正結果のレビューと校了判定**: 校正結果をユーザーに報告し、レビューを行う。
   - **赤字がある場合**: 修正方針の承認を得て前工程（`swe3` 等）へ差し戻し、修正・`test` 再実施の後に再校を行う。
   - **すべての赤字が解消された場合**: ユーザーの明示的な承認をもって **「校了」** とし、完了とする。
   - 校了を妨げない軽微な所見や新たなデザインアイデアが見つかった場合は、ユーザーと合意のうえで `doc/DTP/roughs/stock/` へのストック登録、変更要求（`cr` スキル）、または単位の `README.md` の「既知の課題」へ記録する。

## 校正チェックリスト（出版・エディトリアル品質基準）

Phase 2 の校正では、以下の 4 観点を網羅的に確認する。

### 1. 基本設計・レイアウト（版面・グリッド・余白）

- **判型・版面・マージン**: 外周の余白（マージン）やカード内パディングが窮屈でなく、意図した比率で保たれているか。端（ノド・小口に相当する境界）に重要な文字や要素が接近しすぎていないか。
- **グリッド・整列**: 見出し、本文、図版、カードの端がグリッドラインに沿って揃っているか。意図しない微妙なズレ（1〜数 px の不揃い）がないか。
- **視線誘導と主従関係**: 画面・誌面を開いた瞬間に主役（タイトル・主要図版）へ目が向き、意図した順序で視線が流れる構成になっているか。

### 2. 文字・組版（タイポグラフィ）

- **フォントとジャンプ率**: 指定されたフォントファミリー・ウェイトが適用され、大見出し・中見出し・本文・キャプションの階層（ジャンプ率）が明確か。
- **行間・字間（カーニング・トラッキング）**: 行間（line-height）や字間（letter-spacing）が詰まりすぎ・開きすぎになっておらず、心地よく読めるリズムか。
- **禁則処理・改行位置**: 行頭に句読点や閉じ括弧が来ていないか。見出しやラベルが不自然な位置（単語や助詞の途中など）で折り返されていないか。
- **文字切れ・重なり**: 長いテキストや拡大・縮小表示時に、文字が枠からはみ出したり、省略記号で重要情報が欠落したり、他の要素・線と重なったりしていないか。

### 3. 素材・装飾品質

- **解像度・描画精度**: 画像・SVG・アイコン・シャドウ・グラデーションにボケ、ジャギー、モアレ、クリッピング切れが発生していないか。
- **コントラストと視認性**: 背景色や装飾と文字・線のコントラストが十分で、大画面投影や印刷・閲覧時に判読しにくい箇所がないか。
- **本番素材パスの整合**: 製品から参照される素材がすべて `<プロジェクト>/assets/` 配下の本番素材を参照しており、`doc/DTP/` 配下のストックを直接参照していないか。
- **トーン＆マナーの統一**: 配色、角丸、線の太さ、光彩・影の質感が `doc/DTP/` のスタイル定義と一貫しているか。

### 4. 指定外変化のチェック（あおり校正・デグレ確認）

- **他箇所への波及確認**: 直前の修正によって、無関係なセクション・別スタイル・別モードのレイアウトが崩れたり、要素が消えたりしていないか。
- **目次・見出し・番号の整合**: セクション番号、図表番号、ラベル等の表記に飛びや不一致がないか。
